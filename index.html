Telecraft

An OpenTelemetry estate fails quietly.
Telecraft is what notices.

Source-available fleet and policy management for OpenTelemetry. Telecraft reads what your collectors were told, what they report they are running, and what arrived in your backend, then says which of the three is wrong and who fixes it.

See it running Get a verdict in five minutes

Early software Conformance, authoring and serving all work end to end, with a console over all four workspaces. Interfaces are still free to change.

01

The gap nobody owns

A receiver gets wired into the wrong pipeline, a gateway drops an attribute, a team ships a service with no instrumentation, and nothing announces any of it. The dashboard that should have shown the gap is the dashboard nobody built, because nobody knew the gap existed.

Tools that read collector configuration tell you what was asked for. Tools that read a telemetry backend tell you what turned up. Neither tells you which of those two facts is the problem, so neither tells you whose problem it is.

02

Three readings, crossed

Telecraft reads the estate three ways. Each reading has one definition and one source; they compose, and they are never blended.

  • Intended

    The configuration in git, pinned to a commit SHA rather than a branch tip. A configuration a human committed by hand is Intended too.

  • Effective

    The collector’s own report of the configuration it is running. Never what an applier holds, and never what the platform believes it sent.

  • Observed

    Telemetry that landed in a backend over a window, read through a seam. Each requirement is judged against the window it asked for.

Seven outcomes, because “no logs arrived” is not one situation

Crossing Effective with Observed, per requirement, is what turns “this is broken” into “this is broken, and here is who can fix it”.

The outcome cross
Effective Observed Outcome What it diagnoses
yes yes compliant The requirement is met.
yes no broken_pipeline Somebody configured this and it is not working.
no no not_configured An unmet requirement. The owner needs to instrument.
no yes ungoverned Telemetry is arriving from something nobody configured.
unknown no not_delivered Nothing arrived, and no Effective reading explains why.
no unknown misconfigured A configuration assertion failed, with no signal reading to cross it against.
unknown unknown unknown No evidence from any reading. Never treated as a pass.

A configured pipeline delivering nothing is a defect for the platform team. An unconfigured service delivering nothing is a governance gap for the workload owner. Both score zero; they need different people and different fixes.

Every reading carries a Known flag, and not knowing is a normal state. A provider that cannot answer says so, with a cause. No evidence is never quietly treated as a pass.

03

One binary. A command, or a platform.

There is nothing else to install. The same artefact answers a question in your pipeline and serves the console your teams sign in to, over the same estate, producing the same verdicts.

04

Run it yourself, or let us run it

The same release either way. Nothing sits in the telemetry path in either shape, and your estate is a git repository you own in both.

Cloud

One Organisation is one Instance at an address of its own, your-name.app.telecraft.dev, with its own estate and its own people. It runs Standard Edition, which is the whole product: there is no capability here that a deployment of the same release on your own hardware does not have. What you are buying is the running of it.

  • Who runs it We do. The address, the certificate, the upgrades, the backups, and somebody whose job it is to notice.
  • Signing in Google or Microsoft Entra ID to begin with, and your own provider added by a change to your estate.
  • Getting one Sign-up is a request, not a form that provisions. A person reads it and merges it, so you wait for us rather than for a machine.
  • Serving Not offered here yet. Hosted Organisations read, judge and deliver through git, and the OpAMP endpoint is not published on the internet.
  • Leaving git clone. There is no export format, because the estate is the whole of your authored work and a clone is a complete copy of it.
  • Costs you A subscription for the Organisation. Nothing about your estate is counted.

How the hosted service works

Self-managed

One container image, one Helm chart, or one binary you build. It needs a git repository and a connection to your telemetry backend, and it needs nothing that we operate. An air-gapped deployment is a first-class shape: nothing phones home, and no start-up path reaches the internet.

$ helm install telecraft oci://ghcr.io/telecraft-dev/charts/telecraft \
    --namespace telecraft --create-namespace \
    --set estate.sync.repo=https://forge.example/acme/estate.git
  • Who runs it You do, on your own hardware, at your own address.
  • Getting it The chart above, the image at ghcr.io/telecraft-dev/telecraft, or a binary you build from source.
  • Signing in Basic auth to bootstrap, then any OIDC provider you author into the estate.
  • Serving All of it. The OpAMP endpoint is yours, beside the console, on a port you choose.
  • Air gaps First class. There is no licence server to reach and no telemetry sent back.
  • Costs you Nothing. Standard Edition is unrestricted in production and commercially.

05

Three parts, adopted separately

Telecraft is three capabilities that share one model. Adopt any one of them without the others, in any order; using one is never a condition of using another. Each one states what it costs you.

  • Conformance

    Reads your telemetry backend and your collectors’ reported configuration, judges every Service against the Requirements that apply to it, and routes each finding to an owner.

    Costs you a connection string

  • Authoring

    Teams compose Blueprints from governed Components, and the renderer compiles the result to plain OpenTelemetry Collector YAML in git as change proposals.

    Costs you nothing in your delivery path

  • Serving

    A stateless OpAMP server delivers rendered configuration from git to collectors, with GitOps as a co-equal alternative, chosen per collector.

    Costs you an OpAMP Supervisor beside each served collector

06

Five things that stay true

These hold across every part of the product, in every deployment shape.

  • Nothing sits in the telemetry path. If Telecraft is down, no telemetry stops flowing. It is never a collector, a gateway, or a hop.
  • Git is the source of truth. History, rollback, approval and audit come from git. The console opens change proposals; it never writes to a cluster.
  • Configurations, never binaries. No collector distribution, no container image of your collectors, no chart. Telecraft ships configuration to collectors you already run.
  • The core is vendor-neutral. Backends and fleet managers sit behind seams as plugins, and a lint keeps vendor names out of the core, so independence stays greppable.
  • Air gaps come first. Nothing depends on a hosted service or on a particular git host.

07

See it, then run it

The live demo

demo.telecraft.dev

The real console over a public demo estate: read-only, no sign-in, and built from the latest release rather than from main, so it shows what you can run today.

A first verdict

You need Go 1.26 or later and git. Clone telecraft and the public demo estate beside each other, then:

go build -o telecraft ./cmd/telecraft

./telecraft check \
  -library ../estate-demo/requirements \
  -estate ../estate-demo/demo/rows.yaml \
  -exemptions ../estate-demo/exemptions

The quickstart walks the rest of it, and the documentation covers everything else.
