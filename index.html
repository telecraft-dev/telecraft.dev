Telecraft

Craft, govern, and verify OpenTelemetry across your whole estate.

Telecraft models your collection topology, composes collector configuration from owned, versioned building blocks, and then does the thing no other tool does: it derives from the configuration an expectation of what telemetry should arrive, and checks it. Green means “the configuration worked”, never merely “the configuration applied”.

Early software Conformance, authoring and serving all work end to end, with a console over all four workspaces. Interfaces are still free to change.

01

An estate fails quietly

A receiver gets wired into the wrong pipeline, a gateway drops an attribute, a team ships a service with no instrumentation, and nothing announces any of it. The dashboard that should have shown the gap is the dashboard nobody built, because nobody knew the gap existed.

Tools that read collector configuration can tell you what was asked for. Tools that read a telemetry backend can tell you what turned up. Neither can tell you which of those two facts is the problem, so neither can tell you whose problem it is.

Three readings, crossed

Telecraft reads the estate three ways. Each reading has one definition and one source; they compose, and they are never blended.

  • Intended

    The configuration in git, pinned to a commit SHA rather than a branch tip. A configuration a human committed by hand is Intended too.

  • Effective

    The collector’s own report of the configuration it is running. Never what an applier holds, and never what the platform believes it sent.

  • Observed

    Telemetry that landed in a backend over a window, read through a seam. Each requirement is judged against the window it asked for.

Crossing them is what turns “this is broken” into “this is broken, and here is who can fix it”. A configured pipeline delivering nothing is a defect for the platform team. An unconfigured service delivering nothing is a governance gap for the workload owner. Both score zero; they need different people and different fixes.

Every reading carries a Known flag, and not knowing is a normal state. A provider that cannot answer says so, with a cause. No evidence is never quietly treated as a pass.

02

Three rungs, adoptable separately

Telecraft is three capabilities that share a model. Adopt any one of them without the others, in any order; a higher rung is never a condition of using a lower one. Each one states what it costs you.

  • Conformance

    Reads your telemetry backend and your collectors’ reported configuration, judges every Service against the Requirements that apply to it, and routes each finding to an owner.

    Costs you a connection string

  • Authoring

    Teams compose Blueprints from governed Components, and the renderer compiles the result to plain OpenTelemetry Collector YAML in git as change proposals.

    Costs you nothing in your delivery path

  • Serving

    A stateless OpAMP server delivers rendered configuration from git to collectors, with GitOps as a co-equal alternative, chosen per collector.

    Costs you an OpAMP Supervisor beside each served collector

03

Five principles, and the feature loses

These hold across every part of the product. Where a feature would break one, the feature is the thing that changes.

  • Nothing sits in the telemetry path. If Telecraft is down, no telemetry stops flowing. The platform is never a collector, a gateway, or a hop.
  • Git is the source of truth. History, rollback, approval and audit are git’s, not ours. The console opens change proposals; it never writes to a cluster.
  • Configurations, never binaries. No collector distribution, no container image, no chart. Telecraft ships configuration to collectors you already run.
  • The core is vendor-neutral. Backends and fleet managers sit behind seams as plugins, and a lint keeps vendor names out of the core, so independence stays greppable.
  • Air gaps come first. Nothing depends on a hosted service or on a particular git host.

04

See it, then run it

The live demo

demo.telecraft.dev

The real console over a public demo estate: read-only, and rebuilt from git on every push.

A first verdict

You need Go 1.26 or later and git. Clone telecraft and the public demo estate beside each other, then:

go build -o telecraft ./cmd/telecraft

./telecraft check \
  -library ../estate-demo/requirements \
  -estate ../estate-demo/demo/rows.yaml \
  -exemptions ../estate-demo/exemptions

The documentation walks the rest of it.
